# Visitors 移动端双入口与执行型结果页设计说明

## 背景与目标

`Visitors` 当前已经具备国内旅行规划的基础闭环：

- `web/` 可以提交 `POST /plans` 并打开结果页
- `api/` 已支持 itinerary、地图点位、预算、清单、预约提醒、天气摘要
- 预约提醒坚持“只基于小红书证据，不凭模型臆测”

但当前产品形态仍偏工程原型：

- 首页信息层级偏弱，没有把差异化能力直接表达出来
- `/plan/new` 仍是一整页输入表单，不适合手机端快速填写
- 结果页虽然信息完整，但“预约风险”和“今天怎么走”还没有被提升为首屏主角
- 自驾场景缺少停车与酒店片区建议，无法覆盖周末短途的高频实际问题

本次设计目标是把产品收敛成一个适合 solo 开发、适合移动端打开、同时又具有明显差异化的 V1 形态：

- 首屏支持 `快速生成` 与 `解析小红书` 双入口
- 提单流程改为 `三步向导`
- 结果页首屏突出 `预约可靠性 + 可执行路线`
- 仅在自驾时展示 `停车建议 + 酒店片区停车建议`
- 保持单主方案输出，减少用户决策负担

## 现状与约束

- 技术栈固定为 `Next.js + FastAPI + Supabase + 高德地图`
- 当前真实页面路径：
  - `web/app/page.tsx`
  - `web/app/plan/new/page.tsx`
  - `web/app/plan/[planId]/page.tsx`
  - `web/app/showcase/page.tsx`
- 当前关键前端组件：
  - `web/components/intake/plan-intake-form.tsx`
  - `web/components/result/plan-result-shell.tsx`
  - `web/components/map/amap-plan-map.tsx`
- 当前关键后端模块：
  - `api/app/schemas/plan.py`
  - `api/app/services/planner.py`
  - `api/app/services/plan_store.py`
  - `api/app/services/reservation_hint_service.py`
  - `api/app/services/amap_service.py`
  - `api/app/services/weather_service.py`
- 预约提醒必须继续遵守强约束：
  - 只能来自小红书文本证据
  - 必须展示渠道、价格、证据摘录
  - 若无证据，明确显示暂无证据，而不是猜测
- 产品面向中国境内短途 / 周末 / 节假日出行
- 产品要适合 solo 开发，优先做“结构化内容适配”，不优先做“多套视觉皮肤”

## 方案对比

### 方案一：保留单入口 + 长表单

- 优点：
  - 改动最少
  - 可直接复用现有 `PlanIntakeForm`
- 缺点：
  - 手机端填写负担重
  - 入口层级模糊，无法表达 `快速生成` 与 `解析小红书` 的差异
  - 产品记忆点不足

### 方案二：双入口 + 三步向导 + 执行型结果页

- 优点：
  - 与“无脑堆攻略”的同类产品拉开差异
  - 更适合移动端
  - 能自然承载主模式、偏好标签、自驾停车等结构化输入
  - 能把 `预约风险` 和 `执行路线` 做成首屏能力
- 缺点：
  - 会新增一批请求字段与结果结构
  - 需要重构现有输入页和结果页组件

### 方案三：双入口 + 多套 UI 皮肤 + 多方案结果

- 优点：
  - 视觉上很容易显得“产品化”
  - 满足不同旅行类型的情绪表达
- 缺点：
  - 对 solo 项目过重
  - 容易把资源消耗在皮肤与视觉切换，而不是核心可执行能力
  - 多方案输出会削弱“直接照着走”的定位

## 推荐方案

推荐采用 **方案二：双入口 + 三步向导 + 执行型结果页**。

理由：

- 它把差异化放在真正有价值的地方：`预约可靠性`、`执行感`、`自驾停车信息`
- 它保留足够强的 vibe coding 空间，但不让视觉风格干扰产品逻辑
- 它能利用当前已有后端能力继续演进，而不是推翻重来
- 它最适合 solo 项目：范围可控、验证路径清晰、手机端体验可持续迭代

## 详细设计

### 架构

整体仍使用当前单仓库结构，不新增新的前后端服务：

- `web/` 负责首页双入口、三步向导、结果页模块化渲染
- `api/` 继续负责结构化 itinerary、预约提醒、天气、地图、停车与酒店片区建议的聚合
- `Supabase` 继续作为计划持久化存储层
- `高德地图` 继续用于前端地图渲染与后端地理信息服务

首发不新增额外业务接口，仍以这两个接口为主：

- `POST /plans`
- `GET /plans/{id}`

变化重点在于：

- 扩充 `POST /plans` 请求结构
- 扩充 `PlanRecord` 返回结构
- 前端按新的结构重新组织首屏与结果页层级

### 页面信息架构

#### 1. 首页 `/`

首页采用双入口，但视觉上必须有主次关系：

- 主入口：`快速生成行程`
- 次入口：`解析小红书`

首页首屏内容建议：

- 主标题：强调“30 秒生成一个能直接照着走的国内行程”
- 主按钮：进入 `/plan/new?entry=quick`
- 次按钮：进入 `/plan/new?entry=xiaohongshu`
- 能力卡片：只展示两件事
  - `预约提醒更可靠`
  - `路线可以直接照着走`

#### 2. 输入页 `/plan/new`

输入页改成三步向导，每步只暴露当前必要信息，顶部固定进度条，底部固定主操作按钮。

**第一步：出行基础**

- 城市
- 天数
- 预算范围
- 交通方式

如果交通方式包含 `自驾 / drive / car / self_drive`，则额外显示：

- `parking_required = true`
- `parking_sort = distance | price`
- `max_walk_from_parking_minutes = 30`

**第二步：风格偏好**

主模式单选：

- `出片打卡`
- `城市漫游`
- `自然疗愈`
- `园林民俗`

辅助标签固定选择：

- `美食`
- `夜景`
- `低体力`
- `网红店`
- `安静`
- `学生党`
- `地铁优先`
- `妆造友好`

说明：

- 首发只做“内容结构适配”，不做多套 UI 皮肤
- 主模式和偏好标签会影响生成权重、结果卡片排序和文案语气

**第三步：证据补充**

- 小红书链接
- 小红书摘录 / 手动粘贴证据
- 特殊要求
- 输出语言

如果入口来自 `entry=xiaohongshu`，则第 3 步需要默认高亮，提示“你提供的笔记证据会影响预约提醒与结果可信度”。

#### 3. 结果页 `/plan/[planId]`

结果页采用“首屏结论优先，地图后置”的结构。

**首屏模块排序：**

1. `主方案总览`
2. `预约风险卡`
3. `执行路线卡`

**中段模块：**

- 城市规划图 / 地图
- 小时级时间轴
- 精准预算明细面板
- 准备清单
- 图关系视图（已有 graph 结构）

**自驾专属模块：**

仅当 `parking_required = true` 时展示：

- `景点停车建议`
  - 停车难度
  - 推荐停车场
  - 参考收费
  - 停车场步行到景点时间
  - 排序方式：距离优先 / 价格优先
- `酒店片区建议`
  - 给 2 到 3 个片区
  - 默认按综合最优排序
  - 展示停车方便度、停车成本、去核心景点是否顺路、适合的旅行模式

### 旅行模式与偏好体系

首发只保留 `主模式单选 + 固定偏好标签` 两层结构。

原因：

- 比“多模式混选”更稳定
- 比“纯自由输入标签”更适合手机端
- 后端规则更容易维护

建议映射逻辑：

- `出片打卡`
  - 优先摄影友好、夜景、妆造友好、网红店
- `城市漫游`
  - 优先换乘少、步行串联顺、效率高
- `自然疗愈`
  - 优先安静、舒缓、景观密度适中
- `园林民俗`
  - 优先文化密度、园林节点、需预约文化场馆

辅助标签不单独决定路线，但会参与：

- itinerary 节点倾向
- 结果页卡片排序
- 摘要语气
- 清单与提醒补充

### 自驾停车逻辑

停车不是普通兴趣标签，而是 `出行约束`。

业务规则：

- 只有在用户选择自驾时才展示停车相关输入与输出
- 推荐停车场到景点步行 `30 分钟以内` 视为可接受
- 用户只需要选择排序方式：
  - `距离优先`
  - `价格优先`
- 首发不做“好停优先”第三排序项

停车结果包括两层：

**景点层**

- 停车难度：好停 / 一般 / 难停
- 推荐停车场：可以不是景区本体停车场
- 参考收费：按小时 / 封顶 / 免费等简短说明
- 步行时长：从推荐停车场到景点的预估时间

**酒店片区层**

- 给 2 到 3 个片区
- 以综合最优排序
- 展示停车是否方便、是否顺路、适合什么预算和模式

### 数据模型与接口扩展

#### 请求侧新增字段

建议在 `PlanCreateRequest` 中新增：

- `entry_mode: "quick" | "xiaohongshu"`
- `travel_mode: "photo" | "citywalk" | "nature" | "garden_culture"`
- `preference_tags: string[]`
- `parking_required: boolean`
- `parking_sort: "distance" | "price" | null`
- `max_walk_from_parking_minutes: number | null`

说明：

- `interest_tags` 可以保留给已有能力兼容
- `preference_tags` 用于承接新的固定标签体系

#### 返回侧新增字段

建议在 `PlanRecord` 中新增：

- `execution_summary`
- `reservation_risks`
- `parking_guides`
- `hotel_area_recommendations`

其中：

- `reservation_hints` 继续保留底层证据
- `reservation_risks` 是面向前端首屏的视图模型
- `execution_summary` 是“怎么走更顺”的结果摘要
- `parking_guides` 与 `hotel_area_recommendations` 仅在自驾时返回非空

### 视觉策略与 vibe coding 边界

本产品可以做 vibe coding，但边界必须清楚：

**适合 vibe coding 的部分：**

- 首页氛围
- 排版与动效
- 卡片视觉层次
- 旅行模式标签风格
- 手机端交互节奏

**不适合用 vibe 代替逻辑的部分：**

- 预约提醒证据链
- 预算拆账
- 时间轴结构
- 停车与酒店片区建议
- 天气与准备清单规则

首发推荐视觉方向仍为 `Field Planner`：

- 米白底
- 橄榄绿主色
- 砖红风险强调
- 视觉感受偏“冷静、可执行、有准备”

### 异常与边界处理

- 没有小红书链接：
  - 允许直接生成，不阻塞
- 小红书文本没有预约证据：
  - 不生成虚假预约风险，显示 `暂无证据`
- 未选择自驾：
  - 完全隐藏停车模块
- 地图 key 缺失：
  - 继续展示文字路线与时间轴
- 天气、地图或停车数据缺失：
  - 降级为基础方案，不阻塞主计划结果
- 长内容移动端阅读：
  - 卡片默认展示结论与行动建议，细节折叠
- 结果方案数量：
  - 首发只输出 `1 个主方案`

### 测试策略

#### 前端

- 首页双入口是否带正确 query 参数
- 三步向导的步骤切换与状态保留
- `entry=xiaohongshu` 是否影响第 3 步默认强调
- 自驾场景下停车输入是否出现
- 非自驾场景下停车模块是否隐藏
- 结果页是否把 `预约风险 + 执行路线` 放到首屏

#### 后端

- 新请求字段的 schema 校验
- `entry_mode / travel_mode / preference_tags` 的持久化
- 自驾 / 非自驾两条分支的输出差异
- 停车排序参数的透传
- 没有预约证据时不输出虚假风险

#### 回归验证

- 手机端宽度下首屏顺序是否正确
- `苏州博物馆` 场景下能否同时看到预约提醒与执行路线
- 自驾场景下能否看到停车与酒店片区建议

## 风险与待确认项

- 当前仓库尚无真实停车数据来源，V1 需要明确是：
  - 先基于模板 / 规则输出
  - 还是后续接入真实停车数据源
- 前端尚无成熟组件测试基建，实施时要优先把业务逻辑抽成纯函数并写 node 测试
- `/plan/new` 当前是单页表单，重构成向导时要注意不要打断已有 `POST /plans` 闭环
- 结果页新增模块较多，必须克制：首发只做“最能提升执行感”的内容

## 结论

首发版本的最优解不是“做得更像攻略平台”，而是做成一个 `国内周末出行执行指挥板`：

- 输入更轻
- 预约更可信
- 路线更能直接照着走
- 自驾时停车信息更落地
- 首屏只回答最重要的问题，而不是堆所有信息
