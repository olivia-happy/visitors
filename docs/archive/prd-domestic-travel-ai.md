# 国内旅行 AI 规划产品 PRD

> 文档状态：草案 v1  
> 创建日期：2026-06-22  
> 产品阶段：方案 3  
> 路线定义：V1 先做 AI 工具，V2 升级为完整旅行产品

---

## 1. 产品一句话

一款面向国内旅行用户的 AI 旅行规划工具：用户输入城市、天数、预算、交通方式、住宿风格、兴趣偏好和特殊需求，系统在短时间内生成一份精确到小时、可执行、可分享、带同比例城市规划图的旅行方案。

## 2. 背景与问题

国内旅行信息分散在小红书、地图、天气、点评、票务、酒店、社交平台等多个渠道。对于没有时间做攻略、但又希望准备充分的用户，主要痛点包括：

- 想去一个城市，但完全不了解从哪里开始做攻略
- 能搜到很多内容，但难以整合为一个可执行的方案
- 很难平衡预算、交通、景点分布、住宿位置、体力消耗和预约限制
- 常常漏掉重要准备事项，例如身份证、学生证、充电宝、雨具、衣物、预约时间和购票节点
- 做好的攻略通常是碎片化笔记，不是一个能真正落地执行的完整方案
- 与旅行搭子协作时，信息容易分散在聊天记录里，难以共创

## 3. 产品机会

现有产品大多只解决其中一部分问题：

- 有的擅长搜索内容，但不擅长形成完整计划
- 有的擅长地图和路线，但不擅长行前准备
- 有的能生成泛泛的 AI 行程，但不够中国本地化，不够精确，也不够“J 人友好”

本产品的机会点在于把“国内旅行 + 小红书内容 + 地图路线 + 预算约束 + 准备清单 + 小时级行程 + 分享产物”打通，形成一个真正可执行的旅行方案生成器。

## 4. 产品目标

### 4.1 核心目标

- 帮助用户在 3-10 分钟内完成一份国内城市旅行攻略
- 让最终结果精确到小时，而不是只有模糊的按天安排
- 让用户获得一张同比例缩放的城市规划图，对路线距离和空间分布有直观认知
- 让用户在出发前获得完整准备清单和提醒，不遗漏关键事项
- 让用户可以直接保存、截图、分享，减少二次整理成本

### 4.2 商业目标

- 先验证“J 人旅行规划”需求是否足够强
- 建立“高质量旅行攻略生成”口碑
- 为后续协作、会员、酒店/门票分发、内容分享、旅行后服务打基础

### 4.3 V1 成功标准

- 用户输入一次需求后，可成功生成完整结果页
- 结果页包含：小时级行程、城市规划图、预算拆解、酒店片区建议、准备清单、门票/预约提醒、行前须知
- 方案具备较强国内场景适配能力
- 输出结果可分享、可截图、可导出

## 5. 非目标

以下内容不作为 V1 必做范围：

- 国际旅行全量支持
- 机票/酒店/门票直接下单闭环
- 强社交社区
- 实时导航替代地图 App
- 面向商家或 B 端的管理后台
- 完整 OTA 能力

## 6. 产品形态与分阶段路线

### 6.1 V1：AI 工具

核心定位：输入需求后，快速生成一份完整旅行方案和规划图。

特点：

- 轻量
- 输出结果质量优先
- 不强依赖账户体系
- 适合快速验证需求

### 6.2 V1.5：协作与优化

在 V1 基础上增加：

- 旅行搭子共创
- 行程编辑与版本对比
- 收藏与历史记录
- 更强的提醒和日历同步

### 6.3 V2：完整旅行产品

在 V1.5 基础上升级为完整产品：

- 用户画像长期保存
- 多城市行程
- 行中动态调整
- 旅行后照片整理与内容生产
- 与酒店、票务、地图、日历等服务更深集成

## 7. 目标用户

### 7.1 核心用户

- 22-38 岁的国内旅行用户
- 一二线城市白领、学生、年轻情侣、闺蜜搭子
- 偏好提前规划、不喜欢临时慌乱的“J 人”型用户
- 希望出游体验好，又没有足够时间手工做攻略

### 7.2 典型特征

- 重视效率，希望少做无用功
- 对路线合理性、时间安排、预算控制比较敏感
- 希望“照着走就行”，而不是自己再整理一遍
- 对拍照出片、vlog 记录、妆造友好场景有明确偏好
- 对天气、排队、预约、交通换乘等风险很在意

### 7.3 次级用户

- 周末周边游用户
- 小长假短途用户
- 临时决定出发、但仍想要高质量方案的用户
- 两人或多人出游，需要共创和协调偏好的群体

## 8. 用户需求拆解

用户真正需要的不是“更多信息”，而是以下结果：

- 告诉我去哪里最合适
- 告诉我每天几点做什么
- 告诉我住哪里最方便
- 告诉我怎么控制预算
- 告诉我哪些景点要预约、什么时间订
- 告诉我该带什么、穿什么、注意什么
- 告诉我路线远不远，值不值得这样排
- 告诉我哪些地方适合拍照、出片、做妆造、录 vlog
- 如果我有搭子，告诉我怎么一起协作
- 旅行结束后，帮我把内容变成可分享的表达

## 9. 核心价值主张

### 对用户的价值

- 从“不会做攻略”变成“直接拿到能执行的攻略”
- 从“信息过载”变成“一个整合完成的方案”
- 从“出发前焦虑”变成“准备充分、有底气”
- 从“攻略只是文字”变成“路线、时间、预算、准备一体化”

### 对产品的差异化

- 更适合国内旅行语境
- 更适合没有时间但又想准备充分的人
- 更强调小时级行程，而不是按天粗排
- 更强调同比例地图规划，而不是仅仅列个路线
- 更强调准备清单、预约提醒、穿搭天气等细节
- 更强调小红书内容整合和旅行后分享

## 10. 核心使用场景

### 场景 1：周末短途

用户周四晚上决定周末去杭州，只有两天时间，不想自己翻几十篇攻略，希望快速拿到一份直接能走的路线。

### 场景 2：小长假精细规划

用户计划五一去西安 4 天，希望控制预算、避开排队高峰、住在方便的片区，并且安排适合拍照的景点和时间段。

### 场景 3：小红书灵感转攻略

用户刷到一篇小红书，觉得路线不错，但内容零散，希望系统自动解析链接并生成结构化行程。

### 场景 4：搭子共创

两个人偏好不同，一个喜欢拍照和咖啡馆，一个喜欢自然和安静，希望系统综合偏好给出折中方案。

### 场景 5：旅行后内容生产

旅行结束后，用户想把照片、行程和感受整理成朋友圈、小红书、vlog 文案，不想从头写。

## 12. 关键功能详细定义

### 12.1 需求输入模块

目标：尽可能低成本收集足够多的规划信息。

#### 输入字段

- 目的地城市
- 出发城市
- 出行日期或月份
- 旅行天数
- 同行人数
- 预算范围
- 交通方式偏好：高铁 / 飞机 / 大巴 / 自驾 / 地铁 / 打车 / 公共交通优先
- 住宿风格：酒店 / 民宿 / 青旅 / 精品酒店 / 性价比优先 / 位置优先
- 行程节奏：紧凑 / 适中 / 放松
- 兴趣偏好：拍照出片 / vlog / 咖啡馆 / 美食 / 自然 / 历史 / 漫步 / 购物 / 夜景 / 安静 / 亲子 / 博物馆
- 特殊需求：学生票、老人、无障碍、早起困难、带妆拍摄、低体力、避开人群、必须去景点、不能去项目
- 小红书链接，可选

#### 输入方式

- 表单向导
- 快速模板
- 粘贴自然语言
- 粘贴小红书链接

### 12.2 AI 多 Agent 规划引擎

目标：把不同类型的工作拆给不同 Agent，减少单模型一次性输出的粗糙程度。

#### Agent 角色建议

- 需求理解 Agent：解析用户输入，提炼约束条件
- 城市研究 Agent：收集城市景点、片区、玩法、季节特点
- 路线规划 Agent：根据真实地理位置和通勤时间安排路线
- 酒店片区 Agent：推荐住宿区域与价位段
- 预算 Agent：拆分交通、住宿、门票、餐饮、机动预算
- 天气与准备 Agent：生成穿搭、物品、雨具、防晒、证件清单
- 预约提醒 Agent：识别需预约景点、购票窗口、时间节点
- 小红书解析 Agent：提取热门路线、避坑点、拍照信息
- 地图制图 Agent：输出同比例城市规划图
- 结果审校 Agent：检查冲突、闭馆时间、路径过长、预算超出等问题
- 内容生成 Agent：旅行后生成朋友圈、小红书、vlog 文案

### 12.3 小时级行程模块

目标：让用户拿到“可以直接执行”的方案。

#### 输出内容

- 每一天的起床建议时间
- 早餐、上午、午餐、下午、傍晚、晚餐、夜间安排
- 每个节点的开始时间和结束时间
- 景点停留时长
- 两点之间通勤方式和预计时长
- 景点推荐理由
- 门票、预约、排队风险提示
- 拍照建议时间段
- vlog 或妆造友好提示
- 备选安排

#### 输出要求

- 默认精确到 30 分钟或 1 小时粒度
- 尽量避免频繁折返
- 避免体力负担过重
- 行程节奏需与用户选择一致

### 12.4 同比例城市规划图模块

目标：让用户对城市空间关系和路线距离形成直观理解。

#### 地图要求

- 基于真实经纬度或真实地图路线生成
- 对城市主要活动区域按同比例缩放展示
- 标记酒店片区、每日路线、主要景点、交通节点
- 展示比例尺
- 展示路线顺序编号
- 标注关键通勤时间
- 区分步行、地铁、打车、自驾等路线类型

#### 产出形式

- 结果页内嵌交互地图
- 一张适合截图保存的静态规划图
- 移动端友好的长图或卡片图

#### 设计原则

- 不是做专业 GIS 工具
- 重点是“让普通用户快速理解距离和区域关系”
- 图上信息要能辅助决策，而不是堆满信息

### 12.5 酒店片区推荐模块

目标：用户不一定需要具体某一家酒店，但一定需要知道住在哪个区域更合理。

#### 输出内容

- 推荐 2-4 个住宿片区
- 每个片区的适合人群
- 到主要景点的通勤便利性
- 周边吃饭和夜生活情况
- 安静程度
- 安全感和女生友好度
- 价格区间
- 酒店类型建议

### 12.6 预算引擎模块

目标：用户在确定预算后，系统能在约束内生成可落地方案。

#### 预算拆解维度

- 往返大交通
- 市内交通
- 住宿
- 景点门票
- 餐饮
- 妆造或拍照额外支出
- 购物预算
- 机动预算

#### 预算逻辑

- 输入预算总额后自动分配区间
- 若超出预算，给出降级方案
- 若预算宽松，给出升级建议
- 标记刚性支出与可调支出

### 12.7 准备清单模块

目标：把“事无巨细”的出发前准备结构化。

#### 清单项类型

- 证件：身份证、学生证、驾驶证、医保卡等
- 数码：手机、充电宝、充电器、相机、存储卡
- 衣物：根据气温、下雨概率、昼夜温差、拍照需求给建议
- 洗护与妆造：防晒、卸妆、补妆、发夹、隐形、首饰收纳
- 药品：晕车药、肠胃药、创可贴、过敏药
- 交通票据：身份证明、订单、预约码
- 现金与支付：现金、地铁码、支付方式提醒
- 其他：雨伞、水杯、纸巾、口罩、便携风扇

#### 生成逻辑

- 根据城市天气、季节、景点类型和旅行天数调整
- 根据拍照和 vlog 偏好增加额外建议
- 根据用户身份和特殊需求做个性化提醒

### 12.8 天气与穿搭模块

目标：让用户知道什么时候冷、热、晒、湿、会下雨，进而知道怎么穿。

#### 输出内容

- 出行期间温度范围
- 降水和风力提醒
- 紫外线提醒
- 早晚温差提醒
- 穿搭建议
- 鞋类建议
- 雨具建议
- 防晒建议

### 12.9 门票与预约提醒模块

目标：避免用户“到了才发现进不去”。

#### 输出内容

- 哪些景点需要预约
- 预约渠道建议
- 建议最晚预约时间
- 门票价格区间
- 是否有学生票 / 优待票
- 高峰时段风险
- 闭馆日提醒

### 12.10 小红书链接解析模块

目标：把碎片化攻略转化成结构化规划输入。

#### 能力要求

- 解析链接中的地点、路线、餐厅、住宿、拍照点
- 提取避坑信息
- 提取适合打卡的时间、角度、穿搭建议
- 识别用户是否想“照搬路线”还是“参考改写”

### 12.11 共创协作模块

目标：让旅行搭子可以一起确定方案。

#### V1.5 目标能力

- 邀请链接共享
- 评论和备注
- 偏好合并
- 冲突提示
- 版本记录

### 12.12 旅行后内容生产模块

目标：让旅行结束后，内容还能继续服务用户。

#### 输出能力

- 根据照片和行程生成朋友圈文案
- 生成小红书风格文案
- 生成 vlog 结构提纲
- 生成标题、标签、配文建议

## 13. 核心用户流程

### 13.1 V1 标准流程

1. 用户进入产品
2. 选择目的地城市和天数
3. 填写预算、交通、住宿、偏好、特殊需求
4. 可选粘贴小红书链接
5. 系统开始多 Agent 规划
6. 用户看到生成进度和已完成模块
7. 系统产出完整结果页
8. 用户保存、分享、截图、导出

### 13.2 结果页结构

- 顶部总览：城市、日期、天数、预算、风格标签
- 城市规划图
- 每日小时级时间轴
- 酒店片区建议
- 预算拆解
- 门票与预约提醒
- 天气与穿搭
- 出发前准备清单
- 小红书参考摘要
- 分享导出入口

## 15. 用户体验要求

### 15.1 总体要求

- 输入过程要简单，不超过 3-5 分钟
- 结果输出要“像成品”，而不是像 AI 草稿
- 移动端优先
- 支持整页截图保存

### 15.2 风格要求

- 清晰、可信、克制，不夸张
- 强调“精确、充分、可执行”
- 地图和时间轴要一眼能懂

### 15.3 交互要求

- 重要提醒高亮
- 预算超标要明确提示
- 路线不合理时给出备选方案
- 每日行程可折叠和切换

### 16.3 内容类

- 需要在结果页显式提示用户二次核验官方信息

## 17. 约束与挑战

### 17.1 技术挑战

- 国内数据源分散，结构化难
- 小红书内容解析稳定性和合规性问题
- 地图和路线需要兼顾准确性和速度
- 多 Agent 成本和延迟控制
- “同比例地图”既要真实又要清晰易读

### 17.2 产品挑战

- 输入过多会劝退用户
- 输入过少会导致结果过泛
- 过度细化可能导致行程不够灵活
- 用户对预算和时间准确性期望较高

### 17.3 合规挑战

- 平台内容抓取与引用边界
- 商家信息、票价信息时效性
- 用户隐私与照片内容处理

## 18. 所需团队能力与技能

### 18.1 产品能力

- 用户研究
- 信息架构设计
- 国内旅行场景理解
- 结果页体验设计

### 18.2 工程能力

- Web 前端开发
- 地图与路线服务集成
- 后端接口编排
- 数据缓存与异步任务
- 长结果页渲染与导出

### 18.3 AI 能力

- Prompt 设计
- 多 Agent 编排
- 结构化输出约束
- 内容抽取与重排序
- 小红书笔记解析

### 18.4 数据能力

- POI 数据建模
- 城市片区语义建模
- 票务与天气信息整合
- 预算估算模型

## 19. 关键规则与生成原则

### 19.1 路线规则

- 同一天优先就近安排
- 尽量避免来回折返
- 跨区活动应减少
- 体力消耗与景点密度匹配用户节奏

### 19.2 预算规则

- 先保证刚需，再分配可选体验
- 若预算不够，优先削减可替代项目

### 19.3 准备规则

- 宁可提醒充分，也不要遗漏关键证件和天气风险
- 用户偏好决定清单精细程度

### 19.4 结果质量规则

- 每份结果必须自检冲突
- 若信息不确定，必须标记
- 对时效性强的信息必须附核验提示

## 20. MVP 定义

### 20.1 MVP 必须交付

- 单城市国内旅行
- 1-7 天行程
- 小时级时间轴
- 同比例城市规划图
- 酒店片区推荐
- 预算拆解
- 准备清单
- 天气穿搭建议
- 门票预约提醒
- 小红书链接解析
- 分享导出

### 20.2 MVP 可接受的妥协

- 不直接推荐具体酒店预订链接
- 不保证所有价格完全实时
- 不做复杂协作权限
- 不做多城市联程

## 21. 指标体系

### 21.1 北极星指标

- 生成并被保存或分享的有效攻略数

### 21.2 核心业务指标

- 攻略生成完成率
- 攻略分享率
- 攻略导出率
- 二次编辑率
- 用户复用率
- 历史行程回访率，V1.5 起

### 21.3 质量指标

- 平均生成时长
- 预算偏差反馈率
- 行程不合理反馈率
- 地图与路线错误反馈率
- 清单遗漏反馈率

## 22. 里程碑建议

### 阶段 1：PRD 与方案确认

- 明确 V1 范围
- 确认技术栈
- 确认外部数据源

### 阶段 2：MVP 开发

- 输入页
- Agent 编排
- 结果页
- 地图和预算清单模块

### 阶段 3：内测

- 选择 3-5 个热门城市验证
- 收集路线、预算、提醒准确性反馈

### 阶段 4：增强

- 协作
- 历史记录
- 分享优化
- 内容生产

## 23. 风险与待确认项

- 小红书解析方式如何保证长期可用
- 酒店价格和评分数据从何处获取，是否做实时，还是区间参考
- 门票与预约信息是否依赖第三方，如何处理变更
- 地图是否输出静态图、交互图，还是二者都保留
- 是否先做 Web，还是直接做移动端优先 Web App
- 是否从少量重点城市起步，例如杭州、南京、成都、西安、重庆

## 24. 推荐产品决策

基于当前目标，推荐：

- 第一版做移动端优先的 Web AI 工具
- 先聚焦国内单城市 1-7 天旅行
- 先把“攻略质量 + 地图规划 + 准备清单”做深
- 协作与内容生产放到后续版本

## 25. 附录：V1 结果页理想输出示例

用户输入：

- 城市：杭州
- 天数：2 天 1 夜
- 预算：1500
- 交通：高铁 + 地铁
- 偏好：拍照出片、咖啡馆、citywalk、安静
- 住宿：精品酒店，位置方便

系统输出应包括：

- 一份按小时排好的两天行程
- 一张西湖周边路线规划图，带比例尺和酒店片区
- 酒店推荐片区，例如龙翔桥、凤起路、湖滨
- 每天的交通建议和步行强度
- 西湖、灵隐等景点的预约或高峰提醒
- 下雨是否带伞、建议穿什么鞋、是否要薄外套
- 出发前准备清单
- 可截图分享的成品页
