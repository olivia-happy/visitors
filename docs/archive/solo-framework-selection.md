# Solo 开发者框架选型建议

> 适用项目：国内旅行 AI 规划产品 / vibecoding 产品  
> 目标读者：一个人做完整产品的 solo 开发者  
> 创建日期：2026-06-22

---

## 1. 先说结论

如果你是 solo，而且这个产品要做：

- 小时级旅行攻略
- 城市规划图
- 预算与准备清单
- 小红书链接解析
- 多 Agent 规划
- 分享页 / 长结果页 / 地图交互

我给你的默认推荐是：

### 推荐方案 1：最稳的长期方案

- 前端：`Next.js`
- 后端：`FastAPI`
- 数据库 / BaaS：`Supabase`
- 地图：`高德地图`

适合原因：

- `Next.js` 适合做复杂结果页、分享页、表单和产品壳
- `FastAPI` 适合做 AI 编排、解析、抽取、任务处理
- `Supabase` 适合 solo 快速补齐数据库、登录、存储
- `高德地图` 更适合国内城市路线和地理数据

### 推荐方案 2：最快启动 MVP

- 前端：`Next.js`
- 后端：`Next.js Route Handlers`
- 数据库 / BaaS：`Supabase`
- 地图：`高德地图`

适合原因：

- 全部用一套 TypeScript 很快
- 文件结构简单
- 适合先验证需求，不急着做重 AI 服务

缺点：

- 当你的 AI 逻辑变重后，大概率还要拆出 Python 服务

### 推荐方案 3：如果你特别想全 TypeScript

- 前端：`Next.js`
- 后端：`NestJS`
- 数据库：`PostgreSQL`
- 地图：`高德地图`

适合原因：

- 前后端统一 TypeScript
- 长期工程化更规整

缺点：

- 对你这种 AI 密集型产品，不如 `FastAPI` 顺手
- solo 前期会比方案 1 更重

---

## 2. 你选框架时应该优先考虑什么

你不是在做一个普通博客，也不是在做纯 CRUD 后台。你这个产品的核心难点是：

- 前端结果页复杂
- 地图和空间路线很重要
- 输入表单很多
- AI 输出很长
- 后续会有异步任务
- 未来要支持共创、历史记录、分享

所以你的优先级应该是：

1. 开发快
2. 地图和复杂页面好做
3. AI 能力好接
4. 后续好扩展
5. 一个人能维护

不是：

- 一开始就追求最企业级
- 一开始就上微服务
- 一开始就为“未来 100 人团队”设计

## 3. 前端常用框架

## 3.1 Next.js

### 它适合什么

- 产品型 Web App
- 复杂结果页
- 需要分享、SEO、服务端渲染的页面
- 需要 API 层或轻后端能力的项目

### 优点

- 生态最强
- 资料最多
- React 组件库最多
- 地图、图表、动画、导出、认证方案丰富
- 适合“先做 MVP，再长大”

### 缺点

- 概念比纯前端多
- 如果所有逻辑都堆在里面，后期会变重

### 是否适合你

`非常适合`

---

## 3.2 Nuxt

### 它适合什么

- 喜欢 Vue 风格的 Web 产品
- 需要 SSR、路由、全栈能力

### 优点

- Vue 模板语法直观
- 开发体验很好
- 模块化成熟

### 缺点

- 在你这个场景里，教程、模板和第三方生态通常没有 Next.js 多

### 是否适合你

`适合`

---

## 3.3 SvelteKit

### 它适合什么

- 想要更轻、更简洁的开发体验
- 个人偏好很强的项目

### 优点

- 代码短
- 体验轻
- 写起来爽

### 缺点

- 生态和社区资源不如 React / Vue
- 地图、复杂集成时资料更少

### 是否适合你

`中等适合`

---

## 3.4 React + Vite

### 它适合什么

- 快速做前端 demo
- 纯前端界面验证

### 优点

- 简单
- 启动快
- 轻量

### 缺点

- 不是完整产品框架
- 你要自己补很多 Web 产品能力
- 后续经常还是会转回 Next.js

### 是否适合你

`适合 demo，不是最佳长期方案`

---

## 4. 后端常用框架

## 4.1 FastAPI

### 它适合什么

- AI 产品
- 文本抽取
- 多 Agent 编排
- 异步任务 API
- 结构化输出

### 优点

- 和 Python AI 生态天然契合
- API 写得快
- 文档友好
- 适合做独立 AI 服务

### 缺点

- 如果所有业务都往里堆，后期要自己管理边界

### 是否适合你

`非常适合`

---

## 4.2 NestJS

### 它适合什么

- TypeScript 全栈
- 长期可维护系统
- 权限、协作、复杂业务后台

### 优点

- 工程化强
- 模块化清晰
- 团队协作舒服

### 缺点

- 前期更重
- AI 侧没有 Python 顺手

### 是否适合你

`适合，但不是 solo 的最快方案`

---

## 4.3 Next.js Route Handlers

### 它适合什么

- MVP
- 轻后端
- 前后端同仓

### 优点

- 最快启动
- 部署简单
- 适合快速试错

### 缺点

- 重 AI 任务和长耗时任务会逐渐不够优雅

### 是否适合你

`非常适合 MVP`

---

## 4.4 Django

### 它适合什么

- 管理后台
- 内容系统
- Python 全栈项目

### 优点

- 成熟
- 自带能力多
- 适合后台型系统

### 缺点

- 不如 `Next.js + FastAPI` 灵活
- 对你这种前端交互很重的产品，不是最佳结构

### 是否适合你

`可用，但不推荐优先选`

---

## 4.5 Laravel

### 它适合什么

- 传统 Web 产品
- 后台和 CRUD 很多的项目

### 优点

- 产品能力成熟
- 开发效率高

### 缺点

- 对 AI / Agent / Python 工具链不自然

### 是否适合你

`除非你本身很熟，不然不推荐`

---

## 4.6 Spring Boot

### 它适合什么

- 企业级平台
- 强治理、强规范系统

### 优点

- 稳
- 规范
- 生态成熟

### 缺点

- 对 solo vibecoding 太重
- 第一版成本高

### 是否适合你

`不推荐作为第一版`

## 5. Solo 开发者常用配套技术

这些不一定是“框架”，但对你很关键。

## 5.1 UI 与样式

### 推荐

- 样式：`Tailwind CSS`
- 组件：`shadcn/ui`

### 原因

- 快
- 好拼装
- 很适合 vibecoding
- 做长结果页、表单、卡片、弹层很省时间

## 5.2 表单与校验

### 推荐

- 表单：`React Hook Form`
- 校验：`Zod`

### 原因

- 你的输入项会很多
- 适合做多步骤表单和复杂约束

## 5.3 状态管理

### 推荐

- `Zustand`

### 原因

- 比 Redux 轻
- solo 更容易维护
- 适合表单状态、结果页局部状态、生成进度

## 5.4 数据库访问

### 推荐

- `Prisma`

### 原因

- 好上手
- 对 TypeScript 友好
- 配合 `PostgreSQL / Supabase` 很成熟

## 5.5 认证

### 推荐

- `Supabase Auth`
- 或 `Auth.js`

### 原因

- 你不该自己从零做登录系统

## 5.6 地图

### 推荐

- `高德地图 JavaScript API`

### 原因

- 你的产品是国内旅行
- 国内路线、POI、行政区、交通数据更实用

## 5.7 异步任务

### 推荐顺序

1. 先简单：应用内任务 + 数据库状态
2. 变重后：`Trigger.dev`
3. 更重时：`Celery + Redis`，如果你走 Python 重任务

### 原因

- solo 不要一开始就上复杂队列
- 先把任务流转跑通

## 5.8 部署

### 推荐

- 前端：`Vercel`
- Python 服务：`Railway` / `Render`
- 数据库：`Supabase`

### 原因

- 对 solo 足够快
- 少运维

## 6. 三种最适合你的技术组合

## 6.1 组合 A：最快上线

- 前端：`Next.js`
- 后端：`Next.js Route Handlers`
- 数据：`Supabase`
- 地图：`高德地图`
- UI：`Tailwind + shadcn/ui`

### 优点

- 一个仓库就能先跑起来
- 学习成本低
- 很适合先验证产品

### 缺点

- 后期 AI 逻辑重了会想拆服务

### 适合阶段

`0 到 1 的 MVP`

---

## 6.2 组合 B：最推荐

- 前端：`Next.js`
- 后端：`FastAPI`
- 数据：`Supabase`
- 地图：`高德地图`
- UI：`Tailwind + shadcn/ui`

### 优点

- 前端体验和 AI 服务都兼顾
- 长期成长空间好
- 最符合你的产品形态

### 缺点

- 你要维护两套技术栈：TypeScript + Python

### 适合阶段

`准备认真做产品`

---

## 6.3 组合 C：全 TypeScript

- 前端：`Next.js`
- 后端：`NestJS`
- 数据：`PostgreSQL`
- ORM：`Prisma`
- 地图：`高德地图`

### 优点

- 技术统一
- 长期规范

### 缺点

- solo 前期更重
- AI 工作流不如 Python 直观

### 适合阶段

`你明确不想碰 Python`

---

## 7. 哪个最好

没有绝对最好的，只有最适合你当前阶段的。

如果你是 solo，我的判断是：

### 如果你要最快开始

选：

`Next.js + Supabase + 高德地图`

### 如果你要兼顾 MVP 和长期演进

选：

`Next.js + FastAPI + Supabase + 高德地图`

### 如果你非常想全 TypeScript

选：

`Next.js + NestJS + PostgreSQL`

---

## 8. 我给你的最终建议

如果我是你，我会这样推进：

### 第一步：先做 MVP

- 前端：`Next.js`
- 后端：`Next.js Route Handlers`
- 数据：`Supabase`
- 地图：`高德地图`
- UI：`Tailwind + shadcn/ui`

先做通：

- 输入表单
- 攻略生成
- 小时级时间轴
- 城市规划图
- 准备清单
- 分享页

### 第二步：AI 变重后再拆

把这些拆到 `FastAPI`：

- 多 Agent 规划
- 小红书解析
- 地图制图
- 预算与清单生成
- 长耗时任务

### 第三步：产品化

再补：

- 协作
- 历史记录
- 收藏
- 登录
- 旅行后内容生产

---

## 9. 你现在不要做的事

- 不要一开始上微服务
- 不要一开始做过重的后端分层
- 不要为了“以后可能很复杂”而拖慢 MVP
- 不要一开始就因为框架选择焦虑停住

你的核心任务不是“选最完美框架”，而是尽快做出：

- 好用的输入流
- 精确的攻略结果
- 好看的地图和时间轴
- 可分享的成品页

---

## 10. 一句话答案

如果你只想听一个结论：

### 最推荐

`Next.js + FastAPI + Supabase + 高德地图`

### 最快 MVP

`Next.js + Supabase + 高德地图`
