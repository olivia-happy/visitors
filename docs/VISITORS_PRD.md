## 1. 一句话定位

面向中国境内旅行的**执行型智能行程规划器**：用户输入城市、天数、预算、交通方式、住宿风格与兴趣偏好（可选附一条小红书链接），系统生成一份**精确到小时、可执行、可分享、带同比例城市规划图**的旅行方案。

核心不是"推荐几个景点"，而是**把出发前真正会纠结的信息整理成一份能照着走的方案**。

## 2. 背景与问题

### 2.1 用户侧痛点

国内旅行信息分散在小红书、地图、天气、点评、票务、酒店、社交平台等多个渠道。对"没时间做攻略、但希望准备充分"的用户，痛点集中在六处：

| 痛点 | 具体表现 |
| --- | --- |
| 不知道从哪开始 | 想去一个城市，但完全不了解攻略从哪一步起 |
| 内容多、整合难 | 能搜到大量内容，但难以合并成一个可执行方案 |
| 多约束难平衡 | 预算、交通、景点分布、住宿位置、体力消耗、预约限制互相牵制 |
| 容易漏准备 | 证件、充电宝、雨具、衣物、预约时间、购票节点 |
| 产物不可执行 | 攻略是碎片化笔记，不是一份能落地执行的方案 |
| 协作信息散落 | 与旅行搭子共创时，信息散在聊天记录里 |

### 2.2 为什么"AI 行程生成"没有解决这个问题

市面上已有的产品各解决一部分，但都停在一个共同的门槛前：

- 擅长**搜索内容**的，不擅长形成完整计划；
- 擅长**地图与路线**的，不擅长行前准备；
- 能生成**泛泛 AI 行程**的，不够本地化、不够精确，**最致命的是不可执行**——最常见的产物是一句"建议提前预约"，但不说哪个景点、去哪里约、多少钱、凭什么这么说。

### 2.3 产品缝隙

**把"国内旅行 + 小红书内容 + 地图路线 + 预算约束 + 准备清单 + 小时级行程 + 分享产物"打通成一个真正可执行的方案生成器。**

本产品刻意做得**窄而深**：不做通用旅行聊天机器人，聚焦三件事——**预约可靠性、可执行路线、可控的行程编辑**。

## 3. 目标用户与场景

### 3.1 用户分层

| 层级 | 用户 | 核心诉求 |
| --- | --- | --- |
| 核心 | 国内城市旅行者的周末 / 小长假出行 | "3–10 分钟给我一份能照着走的方案" |
| 核心 | 时间有限、没空做攻略的人 | 不要给我素材，给我结论 |
| 核心 | 在意预算、时间与路线效率的细节型用户 | 每一分钱、每一小时花在哪要看得见 |
| 次级 | 情侣 / 朋友搭子 / 出片路线偏好者 | 方案要能一起看、能改、能分享 |
| 次级 | 自然、安静街区、博物馆、咖啡馆、citywalk 偏好者 | 偏好要能被识别并落到行程里 |

### 3.2 核心使用场景

| # | 场景 | 关键要求 |
| --- | --- | --- |
| 1 | **周末短途**（2 天 1 夜，高铁 + 地铁） | 时间紧，方案必须能直接执行 |
| 2 | **小长假精细规划**（4–5 天） | 景点多，需要路线顺序与体力分配 |
| 3 | **小红书灵感转攻略** | 有一条小红书笔记，希望它变成可执行方案 |
| 4 | **搭子共创**（V1.5） | 多人可编辑、可对齐 |
| 5 | **旅行后内容生产**（V2） | 把行程转成可分享的内容 |

**样例（也是演示预设）**：杭州 · 2 天 1 夜 · 预算 1500 · 高铁 + 地铁 · 偏好拍照出片 / 咖啡馆 / citywalk / 安静 · 住宿要精品酒店且位置方便。
输出应包含：小时级行程、西湖周边带比例尺的路线图与酒店片区（龙翔桥 / 凤起路 / 湖滨）、每日交通建议与步行强度、西湖与灵隐的预约或高峰提醒、下雨是否带伞 / 穿什么鞋 / 是否要薄外套、出发前准备清单，以及可截图分享的成品页。

> **苏州只是录屏与讲解样例，不是产品边界。** 真实使用时用户可输入任意国内城市。

### 3.3 明确不服务的对象

不做 OTA 式的全量旅行平台，不做"只有灵感没有执行"的内容社区。这两类需求各有成熟产品占据，本产品的价值在"从碎片信息到可执行方案"这一段。

## 4. 产品目标与指标

### 4.1 当前阶段（V1 原型）目标

交付**可运行、可演示、可继续开源演进**的完整链路：输入 → 证据预览 → 方案生成 → 结果页 → 行程编辑 → 分享页。作为可公开展示的 AI 产品案例，而不是一个 UI Demo。

### 4.2 上线后的产品指标（分层定义）

| 层 | 指标 | 说明 |
| --- | --- | --- |
| 业务层 | **方案完成率**（走完输入并拿到结果）、**方案采纳率**（用户按方案实际出行）、**分享率** | 是否真的被用于旅行决策 |
| 质量层 | **预约提醒准确率**、**证据可追溯率**（每条提醒能否回指原文）、**误报率**（无预约却提示预约） | 产品的核心承诺是否成立 |
| 系统层 | 方案生成时延（目标 3–10 分钟内出结果）、首屏可读性、地图点位渲染成功率 | 引擎与前端稳定性 |
| 体验层 | 结果页停留时长、编辑台使用率（锁定 / 移除 / 重新优化的平均次数） | 是否真的被"当成方案在用" |

**红线护栏**：

1. **预约提醒必须有证据。** 只在素材显式提到预约要求时生成，**不允许凭模型常识编造**。
2. **每条提醒必须可追溯**到来源链接与原文片段，并附免责声明。
3. **不承诺准确性**：预约政策、门票价格、天气都可能变化，产品给的是"带证据的提示"，不是官方承诺。

### 4.3 V1 成功标准

1. 用户能生成一份完整的城市旅行方案；
2. 结果包含行程、地图、预算、清单与提醒模块；
3. 预约提醒全部基于证据；
4. 预算面板可读、可用；
5. 中文与英文输出都可正常工作。

## 5. 核心流程（已实现闭环）

产品有两个入口，对应两类用户心理——**"我想规划一趟旅行"** 与 **"我看到一条小红书，想把它变成方案"**。

```text
【入口 A · 快速规划】
填基础信息（城市/天数/预算/交通/住宿/偏好/特殊需求）
  → 选旅行风格（节奏、兴趣）
  → 生成方案 → 结果页

【入口 B · 小红书证据优先】
粘贴小红书链接（可选补充文字）
  → 提交前调用 /plans/evidence-preview，先看"这条内容里有哪些预约要求、渠道、价格、证据"
  → 用户确认是否按这条内容规划 → 生成方案 → 结果页

【结果页 · 出行指挥板】
预约风险 · 执行路线摘要 · 小时级时间轴 · 地图点位 · 交通时长
· 预算明细 · 停车建议（自驾时） · 酒店片区 · 行前清单 · 节点关系图

【编辑闭环】
在结果页锁定必去点 / 移除不想去的点
  → 重新优化剩余可调整路线（必去点视为约束，不被优化掉）
  → 用户带着约束继续调方案，而不是只能接受一次性答案
```

**关键设计：预约证据在"提交前"就预览。** 大多数产品的做法是先生成一份看起来完整的方案，用户在结果页才发现关键景点约不上。把证据提取前置到输入阶段，用户可以在花时间生成之前就判断"这条内容靠不靠谱"——**这是本产品与泛旅行生成器最本质的区别。**

## 7. 关键产品决策：AI 边界

| 环节 | 谁负责 | 为什么 |
| --- | --- | --- |
| 需求解析与偏好理解 | 模型 | 自然语言输入需要被结构化为规划参数 |
| 预约证据提取 | **规则 + 原文证据，不靠模型常识** | 预约是本产品最核心的承诺，错一次就毁掉信任 |
| 路线排序与时间轴 | 规划模块 + 地图服务（AMap） | 需要真实地理坐标与交通时长，不能凭空生成 |
| 预算估算 | 规则引擎 + 分类区间 | 必须给出区间与可调项，不能给一个假精确的数字 |
| 天气与穿搭建议 | 天气服务 + 规则 | 输入是实况数据，输出是可执行动作（带伞/换鞋/加外套） |
| 行程编辑与重新优化 | **用户主导** | 必去点由用户锁定，系统只优化剩余可调整部分 |
| 是否出行、是否按方案走 | 用户 | 产品不代订、不代付、不做行程执行 |

**诚实红线（对外叙事的重点）**：

- 预约提醒**只在素材显式提及时生成**（如"需要提前预约""实名预约""公众号预约""免费但是要预约""提前很久预约"），无证据则返回空，**不猜测**；
- 每条提醒都带来源链接与原文片段，用户可自行核对；
- 不提供官方预约验证能力，不做"保证约得上"的承诺；
- 地图、路线、预算均为**辅助参考**，不宣称精确到官方口径。

> 这条边界与另一作品 `moba-build-agent` 的处理方式同源：**未标注的英雄明确披露而不猜测，无证据的预约提醒返回空而不编造**。宁可少给，也不给错的。

## 8. 评测方案

| 层 | 内容 | 状态 |
| --- | --- | --- |
| 后端 | **23 项 pytest**（10 个测试文件）：规划引擎（预算/清单/关系图/执行摘要/预约风险）、地图服务、停车服务、天气服务、预约提示、小红书解析、持久化降级、API 契约 | 已实现 |
| 前端 | ESLint + CI 检查 | 已实现 |
| CI | GitHub Actions 双 job（web: `npm ci` + `npm run lint`；api: `pip install` + `pytest -q`） | 已实现 |
| E2E | 双入口 → 证据预览 → 生成 → 结果页 → 编辑 → 分享 全链路手工实测 | 已实现 |
| 评测边界声明 | 苏州为演示预设，**结果页质量不代表任意城市的真实可用度**；不宣称预约准确率（无真实样本） | — |

**关键测试点**（可直接对照仓库）：

- 预约提示**只在显式证据下**才生成，无预约描述时返回空（反向用例存在）；
- 预算、清单与节点关系图在同一份规划输出中一致生成；
- 自驾模式才附加停车模块，非自驾返回空；
- 天气驱动清单变化（温度/降雨影响清单项）；
- Supabase 未配置时自动降级到本地内存，配置后自动切换。

## 9. 数据与成本边界

| 数据 / 服务 | 来源 | 成本 |
| --- | --- | --- |
| 规划与结果页生成 | 本地服务 | **免费**（无付费 API 调用） |
| 地图点位 / 路线 / 天气 | 高德地图（个人开发者 key） | 免费档，注册即可 |
| 持久化 | Supabase（免费档） | 未配置时自动降级本地内存 |
| 小红书证据解析 | 本地 best-effort 解析，只读链接公开内容 | **免费**，不调付费服务 |
| 用户输入与生成方案 | 用户自己的 Supabase 项目 / 本地 | 使用者需自备 key，仓库不提交任何个人 key |
