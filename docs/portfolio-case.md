# Visitors 作品集项目讲述稿

这份文档用于面试前自查和讲项目，不是对外营销文案。核心目标是让面试官听明白：这个项目不是普通旅游攻略生成器，而是一个围绕国内旅行执行风险设计的智能规划产品。

## 一句话介绍

`Visitors` 是一个面向中国境内周末和假期旅行的智能行程规划器。用户输入城市、天数、预算、交通方式、兴趣偏好和小红书证据后，系统生成一份可以直接执行的小时级方案，并把预约、预算、停车、天气、行前清单和路线关系放在同一个结果页里。

英文版可以这样说：

> Visitors is a China-first AI travel planner that turns scattered trip inputs into an executable city-trip command board, with reservation evidence, hour-level routing, budget, parking, checklist, and editable itinerary controls.

## 为什么做这个项目

我观察到国内旅行准备的真实痛点不是“找不到景点”，而是信息分散且执行风险高。

用户做攻略时通常需要同时打开小红书、地图、天气、票务平台、酒店平台和备忘录。每个工具只解决一部分问题，但没有一个工具能把这些信息整合成“我明天几点去哪里、要不要预约、预算够不够、开车好不好停、需要带什么”的完整方案。

所以我没有把产品定位成泛旅行灵感工具，而是定位成出发前的执行型规划工具。

## 目标用户

核心用户是计划型旅行者，尤其是周末或假期想去国内城市短途旅行的人。

他们通常有这些特征：

- 没有很多时间做攻略，但又不愿意毫无准备出发。
- 对预约、路线、预算、天气、停车这些细节有焦虑。
- 旅行前希望看到一个精确到小时的方案。
- 有些人偏好出片、妆造、网红店，有些人偏好自然、安静、园林或城市漫游。
- 如果是自驾，会非常关心景区好不好停车、附近停车场距离和收费。

## 产品判断

这个项目最重要的判断是：不要做“什么都能推荐”的旅行助手，而是先把两个高频且影响出行成败的问题做深。

### 1. 预约可靠性

国内很多景点不是买票问题，而是“免费但需要提前预约”。比如苏州博物馆本身免费，但用户如果没有提前预约，整个路线就会失效。

因此我把预约提醒前置到输入阶段。用户可以粘贴小红书链接或摘录，系统先解析哪些景点可能需要预约，并展示预约渠道、价格说明和证据摘录。这样用户在生成最终方案前就能发现风险。

### 2. 可执行路线

很多智能旅行产品生成的是一段看起来完整的攻略，但用户真正出发时还要自己判断顺序、距离、交通、预算和准备事项。

所以 `Visitors` 的结果页不是长文本，而是执行型页面：路线摘要、小时级时间轴、地图、预约风险、预算明细、停车建议、酒店片区、行前清单和节点关系图同时出现。

### 3. 可控生成

旅行计划不是一次生成就结束。用户常常会说：“这个点我一定要去”“这个点不想去了”“剩下的能不能重新排一下”。

所以我补了行程编辑台：用户可以锁定必去点、移除不想去的点，再重新优化剩余路线。这个能力能体现我对智能产品的理解：AI 不应该只是给答案，而应该让用户带着约束继续调整答案。

## 核心功能

- 城市、天数、预算、交通方式、住宿风格和旅行偏好输入
- 小红书证据解析和预约提醒预览
- 精确到小时的每日行程时间轴
- 预约提示、预约渠道、价格和证据摘录
- 高德地图点位展示
- 门票、餐饮、住宿、交通等预算拆分
- 天气、穿搭、证件、学生证、雨伞等行前准备清单
- 自驾停车建议，包括停车难度、推荐停车场、距离优先或价格优先
- 酒店片区建议，尤其考虑自驾停车便利性
- 行程数据节点关系图
- 行程编辑：锁定、移除、重新优化
- 中文 / English 切换，明亮 / 暗色主题切换
- 展示页和分享页，方便录屏和作品集展示

## 当前 Demo 怎么讲

推荐面试展示顺序：

1. 打开首页，说明为什么分成快速规划和小红书证据优先两个入口。
2. 打开小红书入口，展示预约证据预览，强调“预约风险前置”。
3. 打开 showcase 结果页，展示路线摘要、预约风险、时间轴、预算、停车和清单。
4. 在行程编辑台锁定苏州博物馆，说明这是预约敏感点，不能随便移动。
5. 移除一个非必去点，再重新优化剩余路线，说明这是可控生成。
6. 打开分享页，说明这个项目可以用于录屏展示和 GitHub 开源下载。

关键表达：

> 我没有让 AI 先生成一份漂亮攻略，再把预约风险藏在后面。我把预约证据放到输入阶段，因为一个关键景点约不上，整条路线都可能失效。

## 和普通旅行生成器的区别

普通旅行生成器通常强调“生成攻略很快”。`Visitors` 更强调“生成的攻略是否能执行”。

差异点可以这样讲：

- 不是只给景点列表，而是给小时级行动方案。
- 不是泛泛提醒预约，而是展示预约渠道、价格和证据。
- 不是只适合公共交通，也考虑自驾停车和酒店片区。
- 不是生成后结束，而是支持锁定、移除和重新优化。
- 不是只做桌面展示，而是移动端优先，方便真实出行中查看。

## 可以体现的产品能力

- 需求分析：从“旅行攻略”拆到预约、路线、预算、停车、天气和行前准备。
- 用户分层：同一城市支持出片、自然、城市漫游、园林民俗等不同偏好。
- 信息架构：把复杂结果拆成预约风险、执行路线、时间轴、预算、地图和清单。
- 风险意识：识别免费但要预约的景点，避免 AI 幻觉式提醒。
- 交互设计：从一次性生成升级到用户可控编辑。
- 工程理解：用 Next.js、FastAPI、Supabase 和高德地图串起完整闭环。

## 目前的取舍

V1 没有追求所有城市和所有景点的官方预约渠道全覆盖，而是先验证“证据优先 + 结构化提醒 + 可执行结果页”的产品路径。

这个取舍是合理的，因为官方渠道全覆盖需要持续维护数据源。如果一开始就追求大而全，反而会牺牲核心链路的可信度和展示完成度。

## 面试可能被问到的问题

### 为什么不用现成大模型直接生成攻略？

因为大模型能生成文本，但不天然保证执行可靠性。旅行场景里，预约、路线、预算和停车任何一个环节出错，都会影响真实体验。这个项目的重点不是“能写攻略”，而是把攻略转成结构化、可检查、可调整的执行方案。

### 为什么预约提醒只依赖小红书证据？

这是 V1 的保守策略。相比让模型猜哪些景点要预约，我更希望先基于用户提供的证据做结构化提取，避免错误提醒。后续可以再接官方渠道校验，把可靠性进一步提高。

### 为什么要做行程编辑？

真实用户不会完全接受一次性生成结果。他们会保留必去点、删掉不感兴趣的点，再希望系统重新安排剩余路线。行程编辑能体现智能产品的可控性，也能提升用户对结果的信任。

### 后续最值得做什么？

第一是接入更真实的距离和时间约束，把当前前端优化演示升级为后端可解释优化器。第二是接官方预约渠道校验。第三是多人共创和旅行后内容生成，例如根据照片生成朋友圈、小红书或 vlog 文案。

## 当前风险

- 部分外部服务需要用户自己配置 key，否则只能看降级 UI。
- 小红书解析在 V1 是 best-effort，不适合作为唯一官方依据。
- 前端仍有少量历史文案需要继续统一。
- 当前路线优化偏演示性质，后续需要接入真实地图距离和预约窗口。

## 推荐简历写法

`Visitors`，国内旅行智能规划工具。基于 Next.js、FastAPI、Supabase 和高德地图实现从旅行需求输入、预约证据解析、方案生成、结果页展示到分享导出的闭环；重点解决国内短途旅行中的预约可靠性、小时级路线执行、自驾停车、预算拆分和行前准备问题；支持中英文切换、暗色主题、行程锁定/移除/重新优化等交互。
